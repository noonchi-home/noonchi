# 실험 기록: 폰 카메라 실시간 화면 속도

> 시작: 2026-10-24 · 상태: 진행 중 · 관련 코드: `web/phone/phone.js`, `web/phone/capture.js`, `web/phone/encoder-worker.js`, `src/phone/feed.ts`

## 목적

대시보드의 클로이드의 눈 칸(폰 카메라 실시간 화면)이 끊겨 보인다. 어디가 느린지 숫자로 찾고, 효과가 큰 순서로 고친다.

## 환경

- 폰: 갤럭시(안드로이드 크롬), WebXR `immersive-ar` + `camera-access`, 같은 와이파이
- PC: Windows 11, twin-home 서버(`HOME_ID=oneroom PHONE_PORT=8210`), 폰 → `/phone/events` 웹소켓 → 서버 → 대시보드 `/api/eye/stream`(MJPEG)
- 한 장이 거치는 단계: 카메라 텍스처 → GPU에서 줄이기 → `readPixels`(GPU → 메모리) → JPEG 변환 → 웹소켓 전송 → 서버 MJPEG → 대시보드 `<img>`

## 측정 방법

```bash
# PC에 실제로 들어오는 장 수(10초)
curl -s --max-time 10 http://127.0.0.1:8200/api/eye/stream -o stream.bin
grep -a -o "Content-Length: [0-9]*" stream.bin | awk '{s+=$2; n++} END {printf "%d장, 평균 %.1fKB\n", n, s/n/1024}'
```

첫 줄은 연결할 때 받는 마지막 한 장이라 실제 장 수는 1을 뺀다. 폰 AR이 켜져 있어야 의미가 있다.

## 기록

| 날짜 | 조건 | 결과 |
|---|---|---|
| 10-24 | 초당 4장 설정, 가로 640px, 메인 스레드 `canvas.toBlob` | 10초에 3장(초당 약 0.3장). 사용자: "폰 화면을 터치해야 바뀐다" |
| 10-24 | JPEG 변환을 워커(`OffscreenCanvas.convertToBlob`)로 옮김, 초당 12장·가로 480px·품질 0.55 | 사용자: 터치 없이 바뀐다. 아직 느리다(장 수는 측정 표시를 넣은 뒤 잰다) |
| 10-24 | 측정 표시 추가, 워커 2개로 동시에 2장 변환, 가로 480px·세로 360px | 실제 폰 측정 대기(폰 ⋯ 메뉴, 대시보드 눈 칸 캡션, `GET /api/eye/stats`) |

## 알게 된 것

- **크롬의 `canvas.toBlob`은 메인 스레드가 한가할 때(idle) 인코딩을 시작한다.** WebXR `immersive-ar` 중에는 페이지 화면을 그리지 않아 한가한 틈이 거의 없고, 화면을 터치하면 그때 틈이 생긴다. 한 장이 끝나야 다음 장을 만들기 때문에 장 수가 사실상 터치 횟수가 됐다.
- **워커의 `OffscreenCanvas`는 메인 스레드 일정과 따로 돈다.** 같은 인코딩을 워커로 옮기자 터치 없이 프레임이 나갔다. 워커를 못 쓰는 브라우저만 `toBlob`으로 대신한다.
- 헤드리스 크롬 확인: 워커 경로에서 JPEG 크기·위아래 방향·서버로 보내는 묶음 형식이 이전과 같다.

## 다음 실험 (추천 순서)

1. **측정 표시 + 동시에 2장 변환 + 크기 줄이기** (구현됨, 실제 폰 측정 대기)
   - 폰 상태 줄에 보내는 장 수, `readPixels`·인코딩 시간, 쌓인 전송량, 건너뛴 이유를 보인다. 서버는 받은 장 수를 대시보드 눈 칸에 보인다.
   - 한 장이 끝나야 다음 장을 만드는 대신 2장까지 동시에 변환한다. 변환이 느린 경우 최대 2배.
   - 대시보드 칸이 작으므로 가로 480px(세로로 들면 360px). 더 줄이면 변환·전송이 빨라진다.
2. **JPEG 대신 영상 압축(H.264, WebCodecs `VideoEncoder`)**: 숫자로 봐도 느리면 이것. 폰의 하드웨어 영상 압축기를 써서 초당 15~30장도 가능하고 데이터가 훨씬 작다. 위치는 지금처럼 따로 보내고 시간으로 맞춘다. 폰 압축과 대시보드 풀기(`VideoDecoder`)를 새로 만든다.
3. **GPU 복사 기다림 없애기(WebGL2 비동기 읽기)**: AR 화면 자체가 버벅일 때. 지금은 `readPixels`에서 GPU가 끝날 때까지 멈춘다. 한 프레임 늦게 꺼내면 멈춤이 없어진다.
4. **WebRTC**: 가장 부드럽고 지연이 짧다. 연결 설정 단계가 추가되고, 프레임마다 위치를 붙이기 어려워 2번보다 손이 더 간다.
5. **안드로이드 앱(ARCore + MediaCodec)**: 웹으로 부족할 때의 마지막 단계. 카메라 이미지를 GPU 복사 없이 받고 하드웨어 H.264로 바로 압축해 초당 30장이 가능하다. 앱 설치(APK)가 필요하고 개발 기간이 길다.
